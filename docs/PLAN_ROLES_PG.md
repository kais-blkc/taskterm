# План: PostgreSQL, роли, инвайты, админка, права задач

> Составлен 2026-11-02. Это план, код пока не менялся. Пункты помечены `[ ]` и отмечаются по мере выполнения.

## Откуда требования

Запрос тимлида (ориентир — Taiga): роли участников и права на редактирование/удаление карточек в зависимости от роли; админка с рассылкой инвайтов на почту и выдачей прав; регистрация только по инвайту, страница входа без регистрации; JWT-токены вместо сессий.

Плюс от нас:
1. БД → PostgreSQL.
2. У задачи есть owner (создатель).
3. Регистрация по инвайтам.
4. Админ-панель.
5. Права на уровне задачи: owner решает, что в ней можно менять (описание, подзадачи: только отмечать / отмечать и добавлять свои).

## Что уже есть в коде (важно для оценки)

- `tasks.authorId` — это уже «создатель». Отдельное поле owner не нужно, достаточно переименовать смысл в API/UI (`owner`) и дать админу возможность передавать владение. Решение — в пункте «Вопросы».
- Нет ролей, нет `email` у пользователей, регистрация по общему `ACCESS_PASSWORD`.
- Сессии: случайный токен в httpOnly-cookie `tt_session`, в БД sha256 (`sessions`). SSE `/api/events` авторизуется этой же cookie.
- Драйвер `better-sqlite3` синхронный: сервисы вызываются как `userByToken(db, token)` без `await`. Переход на Postgres = **все сервисы становятся async**. Это самая объёмная часть работы, поэтому делаем её первой и отдельно.
- Старые миграции SQLite (`apps/api/drizzle/0000`–`0003`) не трогаем (конвенция проекта). Для Postgres заводим новый набор миграций в отдельной папке.

## Принятые решения (предложение, обсуждаем)

### Роли — два уровня
- **Глобальная роль** пользователя: `admin` | `member`. Админ видит всё, управляет пользователями и инвайтами, обходит любые ограничения.
- **Роль на доске** (`board_members`): `owner` | `editor` | `commenter` | `viewer`. Так же устроено в Taiga (роли в проекте). Доска видна только её участникам (и админам).

Матрица прав на доске (задачи):

| Действие | viewer | commenter | editor | board owner / admin |
|---|---|---|---|---|
| Видеть доску и задачи | ✓ | ✓ | ✓ | ✓ |
| Комментировать | — | ✓ | ✓ | ✓ |
| Создавать задачи | — | — | ✓ | ✓ |
| Править/двигать чужие задачи | — | — | ✓ (с учётом политики задачи) | ✓ |
| Удалять задачи | — | — | только свои | ✓ |
| Управлять колонками, участниками доски | — | — | — | ✓ |

Права проверяются в одном месте: `can(user, action, resource)` в `apps/api/src/modules/permissions/`. Роуты и сервисы не содержат `if (role === ...)` — только вызов `can`/`assertCan`. Тестируем матрицу таблично.

### Политика задачи (то, что решает owner задачи)
Колонка `tasks.policy` (jsonb) с разумными дефолтами «всё разрешено»:

```ts
{
  lockTitle: false,
  lockDescription: false,      // описание нельзя менять никому, кроме owner/admin
  lockAssignee: false,
  lockDueDate: false,
  lockMove: false,             // нельзя переносить между колонками
  subtasks: 'free' | 'check_only' | 'check_and_add',
  // check_only      — другие только отмечают пункты, owner правит всё
  // check_and_add   — отмечают + добавляют свои; редактировать/удалять могут только свои пункты
  commentsLocked: false
}
```

- Меняет политику только owner задачи, board owner и admin.
- Owner задачи и admin политику обходят (иначе owner сам себя заблокирует).
- Для `check_and_add` нужен `subtasks.createdBy`.
- Проверка всегда на сервере (включая bulk-ввод чек-листа текстом). В UI поля просто блокируются + подсказка «закрыто owner'ом».
- Применяется и к чужим правкам по SSE: клиент после события перезапрашивает задачу, права из ответа сервера (`task.permissions` — вычисленные флаги для текущего пользователя), клиент сам права не считает.

### Инвайты
Таблица `invites`: `id`, `email`, `tokenHash` (sha256), `role` (глобальная), `boardGrants` (jsonb: список `{boardId, role}`, опционально), `invitedBy`, `expiresAt` (7 дней), `usedAt`, `revokedAt`, `createdAt`.

- Токен случайный, одноразовый, в БД только хэш. Ссылка: `/register?token=...`.
- Регистрация `POST /api/auth/register {token, username, password}`: email берётся из инвайта и не редактируется; после успеха инвайт `usedAt`, пользователю выдаются роль и доступы к доскам из инвайта.
- Страница входа — только логин/пароль, без ссылки «регистрация». Страница `/register` открывается только с валидным токеном (иначе «инвайт недействителен»).
- Отправка на почту: SMTP через `nodemailer` (`SMTP_HOST/PORT/USER/PASS/FROM`). Если SMTP не настроен, админка показывает ссылку, которую можно скопировать и отправить вручную. Так работает в dev и если у команды нет почтового сервера.
- Повторная отправка = новый токен, старый отзывается. Лимит: не больше N активных инвайтов на один email.
- Первый админ: при пустой таблице `users` создаётся из `ADMIN_EMAIL` + `ADMIN_PASSWORD` (env) при старте. `ACCESS_PASSWORD` удаляется полностью.

### Аутентификация: JWT
Чистый stateless-JWT нельзя отозвать, поэтому схема из двух токенов:
- **access JWT** (15 мин, HS256, `sub`, `role`, `ver`) в httpOnly cookie `tt_access` (SameSite=Lax, Secure по `COOKIE_SECURE`). Cookie, а не `Authorization`-заголовок, потому что `EventSource` (SSE) не умеет заголовки, а в localStorage токен держать небезопасно (XSS).
- **refresh token** — случайная строка в httpOnly cookie `tt_refresh` (path `/api/auth`, 30 дней), в БД хранится хэш (`refresh_tokens`: `id`, `userId`, `tokenHash`, `expiresAt`, `revokedAt`, `userAgent`). Ротация при каждом обновлении; повторное использование старого токена = отзыв всей цепочки.
- `users.tokenVersion` (поле `ver` в JWT): смена пароля, блокировка, смена роли → увеличиваем, старые access-токены перестают приниматься. Для блокировки/смены роли это гарантирует, что админ действительно «контролирует».
- Клиент: при 401 один раз дергает `POST /api/auth/refresh`, повторяет запрос; SSE переподключается после refresh.
- CSRF: SameSite=Lax + все мутации только JSON (`Content-Type: application/json`) + проверка `Origin` на мутациях.
- Библиотека: `@fastify/jwt` (или `jose`). Секрет — `JWT_SECRET` в env (обязателен в prod).
- Таблица `sessions` и `tt_session` удаляются в конце этапа 2.

### Админ-панель (`/admin`, только `admin`)
1. **Пользователи**: список (username, email, роль, статус, последний вход), смена роли, блокировка/разблокировка, сброс пароля (одноразовая ссылка), удаление (с передачей задач/досок другому пользователю).
2. **Инвайты**: форма (email, роль, доски и роли на них), список со статусами (ожидает / принят / истёк / отозван), «отправить повторно», «отозвать», «скопировать ссылку».
3. **Доски**: список всех досок, участники и их роли, передача владения.
4. **Журнал действий** (минимальный, `audit_log`): кто и когда выдал инвайт, сменил роль, заблокировал, поменял политику задачи. Показывает тимлиду, что происходит.

Стиль — тот же терминальный, те же правила UI (`Select`, `confirmDialog`, без нативных элементов).

## Риски

- **Async-рефакторинг** (этап 1) трогает весь API. Без git откатить нечем — поэтому этап 0 обязателен.
- **Права «размазаны»**, если проверять их в роутах вперемешку. Решение — один модуль `permissions` и тесты матрицы.
- **SSE и права**: события не должны утекать пользователям вне доски; это нужно проверить отдельным тестом.
- **JWT без отзыва** опасен — поэтому короткий access + refresh в БД + `tokenVersion`.
- **Данные dev-БД**: перенос в Postgres нужен только если там что-то ценное.

## Решения по вопросам (2026-11-02)

1. Роли на двух уровнях: глобальные (`admin`/`member`) + на досках, как в Taiga.
2. SMTP нет — отложено. Инвайт = временная ссылка, админ копирует и отправляет сам; код отправки писем (`nodemailer`) делаем позже, за флагом `SMTP_HOST`.
3. JWT: access + refresh в БД (как описано выше).
4. Данные dev-SQLite переносим в Postgres (скрипт `scripts/sqlite-to-pg.ts`, обязателен в этапе 1). Бэкап: `../taskterm-backups/app-2026-11-02.db` (3 пользователя, 5 задач).
5. Роли `viewer` и `commenter` делаем.
6. Owner задачи = `authorId`, с передачей владения.
